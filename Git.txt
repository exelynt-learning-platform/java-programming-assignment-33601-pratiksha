Version control is a system that records changes to a file or set of files over time so that you can recall specific versions later. Think of it as a "time machine" and a collaborative workspace for your codebase. 
When four developers are building a Java project—such as a fest registration portal, event scheduler, or scoring system—sharing code via WhatsApp, Google Drive, or USB drives quickly leads to chaos. Here is why version control is essential for your team:
Simultaneous Work Without Overwriting Code, Clear Accountability and Progress Tracking, Smooth code integration.

1. Lost Code

• The Problem: When developers keep files only on local hard drives or pass around manually named folders (like project_final_v2), a hardware failure, accidental deletion, or misplaced folder wipes out hours of work permanently.
• Concrete Example: Developer A spends three days building a new user authentication module on their laptop. Before they email the files to the team, their laptop suffers a hard drive crash. With Git, Developer A would have pushed daily commits to a remote repository (such as GitHub or GitLab), allowing them to download the exact code onto a replacement machine in minutes.

2. Overwritten Edits

• The Problem: When two people edit the same file on a shared network drive or upload files over each other via FTP/cloud storage, the last person to save silently erases the other person's changes.
• Concrete Example: Developer A fixes a checkout bug in payment.js and uploads it to the shared folder at 2:00 PM. Developer B had opened an older copy of payment.js at 1:30 PM to add a discount code feature and uploads their version at 2:05 PM—completely wiping out Developer A's bug fix. With Git, branching and merging detect that both developers modified the same file, automatically combining non-overlapping edits or flagging a merge conflict so both changes are safely reviewed and kept.

3. No History (Accountability & Rollbacks)

• The Problem: Without a record of what changed, when it changed, and who changed it, teams cannot easily undo broken updates or understand why a piece of code was written a certain way.
• Concrete Example: The team's live website crashes on Friday afternoon, and nobody knows which recent update caused the failure. Without Git, the team has to manually read through thousands of lines of code guessing what changed since Tuesday. With Git's commit history (git log and git revert), the team can see every change made since Tuesday, identify the exact commit that introduced the bug, and roll back the site to a working state with a single command.

Git is the version control tool running on each team member's laptop, while GitHub is the cloud platform where the fest team stores, shares, and merges everyone's work.

The main difference between centralized and distributed version control is where the full project history is stored: centralized version control keeps the complete repository and history on a single central server, while distributed version control gives every developer a full local copy of the entire repository and its history
